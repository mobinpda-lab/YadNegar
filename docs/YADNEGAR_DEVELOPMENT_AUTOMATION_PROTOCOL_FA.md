# پروتکل استاندارد توسعه، خودکارسازی و بهینه‌سازی یادنگار

## هدف
هدف نهایی، تولید یک محصول واقعی، پایدار، قابل استفاده و آماده انتشار است؛ نه صرفاً سالم بودن محیط توسعه یا کارخانه نرم‌افزار.

## اصول اجرایی
1. **PRODUCT FIRST** — هر تصمیم فنی، خودکارسازی یا اصلاح فرایند باید مستقیماً به تکمیل، کیفیت، پایداری، تجربه کاربری یا آمادگی انتشار یادنگار کمک کند.
2. قبل از هر تغییر، **Fresh Audit** از وضعیت زنده GitHub انجام می‌شود.
3. کارهای مستقل تا حد امکان **موازی، همزمان و کنترل‌شده** اجرا می‌شوند.
4. کارهای وابسته با ترتیب درست اجرا می‌شوند و هیچ موازی‌سازی نباید پوشش تست یا کنترل کیفیت را کاهش دهد.
5. تغییرات کوچک، قابل بازگشت و قابل بررسی باشند؛ از تغییرات بزرگ و بازنویسی غیرضروری پرهیز می‌شود.
6. هیچ تغییر، تست، Build، CI، Merge یا Automation به‌عنوان انجام‌شده اعلام نمی‌شود مگر اینکه در GitHub واقعاً قابل تأیید باشد.

## تقسیم کار
پس از Audit، کارهای باقی‌مانده به سه مسیر تقسیم می‌شوند:
- **محصول/هسته:** منطق کسب‌وکار، مدل، Repository/Storage و قابلیت‌های اصلی.
- **رابط/قابلیت:** RTL، App Shell، ناوبری، صفحات و جریان‌های کاربری.
- **کیفیت/خودکارسازی:** CI/CD، تحلیل، تست، Build، Smoke Test، گزارش و کنترل انتشار.

## جریان کیفیت و CI/CD
در صورت مستقل بودن مراحل، این جریان به‌صورت موازی اجرا می‌شود:

`Analyze ‖ Unit Test ‖ Widget/Integration Test ‖ Build → Smoke Test`

Smoke Test پس از آماده شدن Build اجرا می‌شود. موازی‌سازی فقط زمانی انجام می‌شود که وابستگی واقعی بین مراحل وجود نداشته باشد.

## سناریوهای محصول
سناریوهای مستقل تا حد امکان جداگانه و موازی اعتبارسنجی می‌شوند:
- راه‌اندازی برنامه
- رابط کاربری و RTL
- جریان‌های اصلی کاربر
- قابلیت‌های مستقل
- عملکرد بخش‌های حساس
- آزمون‌های Release

## معیار تصمیم‌گیری
برای هر تغییر، ترتیب بررسی این است:
**ارزش محصول → تغییر فنی لازم → کیفیت و عملکرد → خروجی قابل استفاده**

اگر یک Foundation یا زیرساخت برای حرکت محصول لازم نباشد، ساخته نمی‌شود.

## خودکارسازی
تا حد امکان این موارد باید خودکار شوند:
- مدیریت و تشخیص کارهای باقی‌مانده
- بررسی تغییرات
- اجرای تست‌ها
- Build
- کنترل کیفیت
- اعتبارسنجی Release
- تولید گزارش وضعیت

هدف، افزایش تدریجی سطح خودکارسازی در هر چرخه توسعه است.

## کنترل تغییر
ترتیب استاندارد:
**Audit → Risk Check → Implement → Test → Report → Commit/PR**

هر Commit باید کوچک، هدفمند و قابل بازگشت باشد.

## تعریف موفقیت
فرایند موفق است وقتی بتواند به‌صورت قابل اندازه‌گیری و تکرارپذیر به این زنجیره برسد:

**Foundation موردنیاز → CI سبز → Build موفق → هسته پایدار → قابلیت‌های اصلی → تست محصول → Smoke Test → اعتبارسنجی انتشار → RELEASE-READY**

این سند مرجع اجرای چرخه‌های «ادامه یادنگار» است.
